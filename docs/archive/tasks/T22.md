Notes first, repos later. Notes are local MDX with no API, no rate limit, and no cache to fight, so the mechanic gets proven here before it touches GitHub.

## The rule

**Companions come from bodies of work. XP comes from activity.**

A single note is activity. A cluster of notes about one thing is a body of work.

| Source | Produces |
|---|---|
| A tag with **5 or more** notes | A companion, themed by what the cluster is about |
| Any single note | XP only |

A note below the threshold is a **seed**: it gives XP, hatches nothing, and may grow into a cluster later. That is thematically right for a garden and it is the answer to "what about a plain note", so do not special-case it into hatching something.

## Three things that must be true

**1. XP is never either/or.** Every note gives XP to the main garden creature, always, whether or not it belongs to a cluster. Hatching is an additional event on top, not an alternative.

**2. A hatching companion inherits its cluster's XP.** It must NOT start at stage 1. Compute its XP from the notes in its own cluster (their word counts, wikilinks, backlinks, maturity) and resolve its stage from that. A companion emerging from five real notes should already be partly grown, otherwise the mechanic punishes work already done.

The main garden creature keeps counting those same notes. The double count is deliberate: the garden creature is the aggregate, a companion is a slice.

**3. Assignment is deterministic and semantic.** Same cluster always gives the same species. Derive the theme from real signal, in priority order:
- The tag name itself (`design`, `music`, `security`)
- Titles and descriptions of the notes in the cluster
- Fall back to a hash of the tag name so nothing is ever empty

Map themes to the species lines already defined in `src/lib/game/sprites/species.ts`. Reuse that data, do not invent a parallel system. Add theme keywords for note-shaped topics: writing, reading, thinking, design, learning, tools.

## The hatch should feel like an event

The user's word for this was "gacha", and what they meant was **discovery**, not chance. There is no randomness here. But a companion appearing should read as something that happened, not as a row quietly added to a table.

On `/companions`, newly hatched companions need a visible distinction from long-standing ones. A "new" marker, a distinct treatment, something. Keep it within the archive design language: one accent, sharp edges, no confetti.

Since there is no persistence, "new" has to be derived, for example a cluster that only just crossed its threshold. If you cannot derive it cleanly without storage, say so in your report rather than inventing a storage layer.
