# T25. Garden editor: layout, controls, and the sprite mismatch

Three problems, all visible in real screenshots. Read them in order; the third is the smallest and I may take it myself.

---

## Problem 1: the editor layout is a form, not a writing surface

Current shape is a two-column split with a stacked form above the body: `TITLE` input, `TAGS (COMMA SEPARATED)` input, `MATURITY` dropdown, then a text area. Three labelled form fields eat the top third of the pane before any writing happens.

Obsidian gets this right by making the note *look like a note*: the title is the heading, metadata is a thin strip, and the body owns everything else.

**`/garden` becomes a workspace, not a page with an editor stuck to it.**

Two distinct states, and this is the structural change:

- **Not connected:** the current explanatory page. Hero copy, what this does, why nothing uploads, a Connect button. Marketing, essentially.
- **Connected:** a full-height Obsidian-style workspace. The hero copy disappears entirely. This is a tool now, and the writing surface owns the screen.

```
┌────────────────┬────────────────────────────────────┐
│ ⌕ filter       │  My Note Title            [Save]   │
│ + New note     │  #writing #thinking    ○ ◐ ●       │
├────────────────┼────────────────────────────────────┤
│ ▾ writing    4 │                                    │
│   Evergreen…   │  Body owns the rest of the height  │
│   Learning…    │                                    │
│   On Writing…  │                                    │
│ ▾ meta       3 │                                    │
│   Graph View   │                                    │
│ ▾ untagged   1 │                                    │
│                │                                    │
├────────────────┤                                    │
│ 🌱 Mossling L2 │                                    │
│ ▓▓▓░░░ 575 xp  │                       +140 xp      │
└────────────────┴────────────────────────────────────┘
```

**The creature lives at the bottom of the sidebar.** Reasons, in case a different placement seems better:

- The note list is the primary tool and deserves the top.
- Bottom-left is where status and identity live in almost every app of this shape: Obsidian, VS Code, Slack, Discord. It will feel familiar without anyone thinking about it.
- It stays visible the whole time you write, which is the entire loop: write a note, watch the thing grow. Ambient, in the corner, never demanding attention. Same instinct as Taskbar Hero.

Keep it compact: sprite, name, stage, a thin XP bar. Clicking it goes to the full creature view. It is a status readout, not a dashboard.

Specifics:

- **Group the note list by tag**, with collapsible headers and a count. The current flat list already shows tags per row, which is noisy and hard to scan. A note with several tags may appear under each; that is correct and matches how Obsidian tag panes behave. Untagged notes get their own group at the end.
- **A filter box** at the top of the list. Matches title and tag. Seven notes do not need it; seventy do, and someone connecting a real vault will have hundreds.
- **Title becomes an inline heading** in the editor pane, styled like the note's own H1, editable in place. No `TITLE` label above a bordered box.
- **Metadata strip** under the title: tags as chips with an inline add, maturity as a control (see problem 2). One line, not two labelled rows.
- **The body fills remaining height.** It is the point of the screen.
- Keep the live XP preview, but move it out of the way; a footer line is fine.

**Simple, not a clone.** Obsidian has panes, tabs, splits, plugins, a command palette. Build none of that. What is being borrowed is the *shape*: a persistent list on the left, one note filling the rest, metadata thin and out of the way. Everything else is scope creep.

Deliberately out of scope: tabs, split panes, drag-to-reorder, a command palette, folders as a second hierarchy, graph in the sidebar.

**Height behaviour.** A workspace needs real height. Use `min-h-[100dvh]` minus the navbar, never `h-screen`. The sidebar and editor scroll independently; the page itself must not scroll horizontally at any width. Below `md`, collapse to a single column: the list becomes a toggleable drawer, so the editor still works on a narrow window.

## Problem 2: the native dropdown looks broken

The `MATURITY` field is a bare `<select>`, so it renders with OS chrome: a light popup on a dark page, ignoring every theme token. The screenshot shows exactly this.

**Replace it with a three-option segmented control**, since maturity has exactly three values and they are ordered:

```
○ seedling   ◐ budding   ● evergreen
```

Same glyphs `MaturityMark.tsx` already uses, so it matches the rest of the site. Styled with the theme tokens, works in both themes, keyboard operable (arrow keys between options, proper `role="radiogroup"`), and no native popup anywhere.

**Audit for other native controls** while you are in there. Any other bare `<select>` has the same problem.

## Problem 3: `/garden` shows the wrong creature

The home page shows **Oddish**. `/garden` shows the local hand-drawn pixel sprite. Same stage, two different creatures, which reads as a bug because it is one.

Cause: `CreatureSprite` resolves PokeAPI server-side and transitively imports `node:fs` through `sprites/pokeapi.ts`, so a client component cannot use it. T23 correctly fell back to the local sprite rather than breaking the page.

Fix: `src/lib/game/sprites/pokeapi-cache.json` is already committed to the repo, and a JSON import is just data with no `fs` involved. Split `pokeapi.ts` the same way `stats-from-items.ts`, `clusters-from-items.ts`, and `streak.ts` were split:

- a **pure** module that maps a `StageId` to its sprite URLs by reading the committed cache, importable from a browser
- the existing **fs** module that writes and refreshes that cache at build time

Then the client garden renders the same animated sprite as every other surface, with the local sprite still there as a genuine fallback.

**This is now the fourth `fs`-in-the-client split.** If a fifth appears, the real fix is a lint rule banning `node:fs` imports from anything reachable by a `'use client'` component. Worth proposing if you see it.

- Keyboard operable, and state never conveyed by colour alone.
