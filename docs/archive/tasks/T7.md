## The endpoint

```
GET /api/creature.svg?user=<handle>            -> image/svg+xml
GET /api/creature.svg?user=<handle>&repo=<name>
GET /api/creature.svg?user=<handle>&theme=dark  -> optional, defaults to light
```

Renders: the creature sprite, its name, stage (`N of 4`), and an XP bar. Keep it compact, roughly 400x120, since it sits inline in a README.

## Hard constraints, already established

**This must be a STATIC SVG.** GitHub proxies all README images through its camo cache. CSS animation inside an SVG is stripped or ignored, and SMIL is unreliable through camo. Do not ship an animated SVG and claim it works.

That rules out the PokeAPI GIF path for this surface. **Use the local `SpriteData` sprites**, drawn as SVG `<rect>` elements. This is exactly why sprites are stored as data rather than image files: `src/lib/game/sprites/` gives you a palette plus pixel rows you can emit directly as rects.

Do **not** reference an external image URL from inside the SVG. GitHub's proxy will not fetch it, and it would leak a request per view anyway.

Other constraints:
- `Content-Type: image/svg+xml`
- Cache headers, and support a cache-busting query param, since camo caches aggressively
- **Readable in both GitHub themes.** GitHub serves one image to light and dark readers, so either respect a `theme` param, or pick colours that hold up on both light and dark backgrounds. State which approach you chose and why.
- Every string inside the SVG must be XML-escaped. A handle or repo name containing `&` or `<` must not produce malformed XML.
- Zero em-dash characters in any visible text.

## Failure behaviour

Must always return a renderable SVG, never a 500 and never an error page, because a broken image in someone's README is worse than a degraded one.

| Case | Expected |
|---|---|
| `user` missing | A small SVG reading "user parameter required" |
| Handle does not exist | A small SVG saying so |
| GitHub degraded or rate-limited | A stage 1, zero XP creature, same as T6's fallback |
