# T16. Test the delivery surfaces: API, badge, sprites, extension

**Depends on** T10 (done) · parallel-safe with T15

Everything that ships to *other people* is currently protected by nothing. The API, the README badge, the sprite system, and the extension were each verified once by hand and never again. This task makes those verifications repeatable.

The extension is the sharpest gap: it was confirmed working once, with screenshots, by an agent. Nothing would tell us if it broke tomorrow.

## Priority 1: sprite validator as a test

`src/lib/game/sprites/validate.ts` already exists but only runs as a manual script, so a malformed sprite fails **nobody**. Wrap it: assert all sprites in the registry pass. Also assert it still fails loudly on bad input (wrong row count, wrong row length, unknown palette index, `palette[0]` not `'transparent'`, a malformed colour string).

Cheapest high-value item here. Do it first.

## Priority 2: `svg-render.ts`

The badge ships into other people's READMEs, where a malformed SVG renders as a broken image.

- Output is **well-formed XML**. Parse it, do not regex it.
- **XML escaping**: a handle or repo containing `& < > " '` produces valid output. This is the one that breaks READMEs.
- **No animation**: no `<style>`, no `<animate>`, no SMIL. GitHub's camo proxy strips them, so their presence means the badge is lying about being static.
- **No external references**: the only URL in the document should be the SVG namespace. An `<image href="https://...">` would never load through camo.
- The `var(--sprite-outline)` palette entry is resolved to a concrete colour, since a CSS variable is meaningless outside the site's DOM.
- Both `theme=light` and `theme=dark` produce readable colour pairs.

## Priority 3: API route contracts

Mock `fetch`. **No live GitHub calls**, tests must be deterministic and offline.

For `/api/creature`:
- Missing `user` returns 400 with a JSON body
- Invalid handle shape is rejected **before** any fetch, and the rejection is a 400
- Nonexistent handle returns 404 with a JSON body
- Upstream rate limit returns **200 with a degraded creature**, never a 500
- **The garden asymmetry**: a non-owner response has all garden stats zeroed and contains no garden items. This is the leak this project has already had twice, so assert it hard.
- A cache hit makes **zero** fetch calls
- CORS headers present, `OPTIONS` handled

For `/api/creature.svg`: every failure case returns SVG at 200, never JSON and never a 500.

## Priority 4: extension core logic

`extension/common/core.js` holds the pure logic: cache TTL, URL building, batching, theme detection. Test it directly by importing the module in Node. No browser needed.

- Cache respects its TTL, and a fresh entry means zero fetches
- API URL construction is correct for both the user and user-plus-repo shapes
- Bounded concurrency and the 30-repo cap actually bound
- Theme detection reads `data-color-mode` and falls back sensibly
- **A failed API call degrades quietly** and never throws, since throwing into a host page is the worst outcome

If `core.js` is not importable in Node because it assumes browser globals, **say so** and test what you can with a minimal stub rather than restructuring the file. That would be a finding worth reporting: it means the logic is not independently testable.

Full end-to-end browser automation of the extension is **out of scope**. Note it as the remaining manual step.
