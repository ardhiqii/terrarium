# T27. Guard against `node:fs` reaching the client bundle

**Depends on** everything through T26 (merged to `dev`)
**Read first:** `AGENTS.md`, then the history below. The history is the spec.

## Why this exists

Four separate times, a Node built-in reached a `'use client'` component and **took down every route on the site**:

| Leak | Chain |
|---|---|
| 1 | `ConnectGarden` -> `clusters.ts` -> `backlinks.ts` -> `fs` |
| 2 | `ConnectGarden` -> `repo-creature.ts` -> `items.ts` -> `content.ts` -> `fs` |
| 3 | `ConnectGarden` -> `repo-creature.ts` -> `github.ts` -> `node:fs` |
| 4 | `ConnectGarden` -> `CreatureSprite` -> `sprites/pokeapi.ts` -> `node:fs` |

Each was fixed by extracting a pure module (`stats-from-items.ts`, `clusters-from-items.ts`, `streak.ts`, `pokeapi-pure.ts`). A fifth will happen. Catching it by hand is not a plan.

**What makes this expensive:** Turbopack fails the whole build on one bad module, so a single leak 500s every route, not just the offending page. And `npx tsc --noEmit` and `npm test` both pass while the app is completely dead, because unit tests never load the browser bundle. The gates are green and the site is down.

## The critical design point, read this before choosing an approach

**A lint rule that flags direct `node:fs` imports inside `'use client'` files would have caught ZERO of the four leaks.** Every single one was transitive: the client component imported something clean, which imported something clean, which imported `fs` three or four hops down.

So the check must **walk the import graph**, not inspect single files. If you reach for an off-the-shelf ESLint rule, verify it does transitive analysis before adopting it. Most do not.

## Build

A test at `src/lib/client-bundle-safety.test.ts` (name it as you like) that:

1. Finds every file under `src/` whose first non-comment line is `'use client'`.
2. Walks the import graph from each, following relative and `@/` imports, resolving `.ts`, `.tsx`, `/index.ts`. Handle cycles; the graph has them.
3. Fails if any reachable module imports a Node built-in: `fs`, `node:fs`, `path`, `node:path`, `os`, `node:os`, `child_process`, `crypto`, `node:crypto`. Bare `crypto` is ambiguous (there is a web `crypto`) so treat only `node:crypto` as a violation and say so in a comment.
4. On failure, prints the **full chain** (`ConnectGarden.tsx -> repo-creature.ts -> github.ts -> node:fs`), not just the offending file. The chain is what makes it fixable in one pass.

No new dependency. A regex-based import extractor over the source text is sufficient and honest; a full TypeScript-compiler-API walk is more correct but heavier, so pick one and state the tradeoff. Do NOT run `npm install`.

## Prove it actually works

A test that passes on a clean tree proves nothing. **Demonstrate it catches a real leak:**

1. Temporarily add `import { existsSync } from 'node:fs'` to a module a client component reaches transitively (`repo-creature.ts` is the natural choice, it is 2 hops from `ConnectGarden`).
2. Confirm the test fails and prints the full chain.
3. Revert.

Put the observed failure output verbatim in your report. Without this step you have written an assertion nobody knows fires.
