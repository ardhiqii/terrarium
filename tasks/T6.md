## Endpoints

```
GET /api/creature?user=<handle>              -> CreatureState as JSON
GET /api/creature?user=<handle>&repo=<name>  -> that repo's creature
```

### The garden asymmetry, and it matters

`getCreatureState()` computes garden XP from **local MDX files**, which only exist for the owner of this site. An arbitrary GitHub handle has no garden here.

So:
- **Owner handle** (`ardhiqii`, read from `GITHUB_LOGIN` env, do not hardcode): garden XP plus commit XP, the full creature.
- **Any other handle**: commit XP only. Garden stats are zeroed, not faked, and not borrowed from the owner's content.

Getting this wrong means every stranger's creature shows the owner's note count, which would be an obvious and embarrassing bug. Handle it explicitly and test it.

### Repo creature

`repo-creature.ts` computes a `CreatureState` from a single repo's commit activity. Reuse `resolveStage`, `computeCommitXp`, and the existing item logic. Garden stats are zeroed. Document what an item unlock means for a repo creature, or exclude items from repo creatures and say so.

## Caching is the whole ballgame

The browser extension will call this **on every GitHub page view**, potentially several repos at a time. Uncached, this exhausts the GitHub rate limit almost immediately and gets the token throttled.

1. **Response cache headers.** `Cache-Control: public, s-maxage=3600, stale-while-revalidate=86400`. One upstream refresh per handle per hour, and stale content served instantly while revalidating.
2. **An in-process cache** keyed by `user` and `repo`, so repeated hits inside one server instance do not refetch.
3. **Never call GitHub on a cache hit.** Prove this with a fetch spy in your verification.

Budget check: GitHub GraphQL allows 5000 requests/hour authenticated. At one refresh per handle per hour, that supports thousands of distinct users. Without caching, a single active extension user could burn hundreds of requests an hour on their own.

## Failure behaviour

Every one of these must return a valid, renderable response, never a 500 and never a thrown exception:

| Case | Expected |
|---|---|
| `user` param missing | 400 with a JSON error body |
| Handle does not exist | 404 with a JSON error body |
| GitHub rate-limited upstream | **200 with a fallback creature** (stage 1, zero XP) plus a flag indicating the data is degraded. Do not fail the extension's page render because GitHub is busy. |
| Network unavailable | Same as rate-limited, serve stale cache if present |
| `repo` given but does not exist | 404 with a JSON error body |
| No `GITHUB_TOKEN` configured | Works via the unauthenticated path, undercounted, still returns 200 |

## Other requirements

- **CORS.** The extension calls this cross-origin from `github.com`. Set permissive CORS headers and handle the `OPTIONS` preflight.
- **Rate limit per IP.** A simple in-memory counter is acceptable at this stage. Document that it resets per instance and is not a real distributed limiter.
- **Validate the `user` param** against GitHub's actual handle rules before putting it in a URL. Reject anything else with a 400. Do not pass unvalidated input into a fetch.
- **Never leak the token.** Not in a response body, not in an error message, not in a log line.
